# Masseberegning — as built

Written 2026-09-09, updated 2026-09-11. Records what was actually implemented
against `claude/deployment-and-auth-plan.md` and
`claude/invitation-link-design.md`, and where the code deviates from those
designs.

**Status: deployed and working.** `README-DEPLOY.md` in the repo is the runbook.

| | |
|---|---|
| Repo | `github.com/kongper/Masseberegning`, personal account, **public** |
| UI | GitHub Pages at `https://kongper.github.io/Masseberegning/` |
| API | Google Cloud Run, `masseberegning-api`, `europe-north1` (Finland), one instance |
| Database + sign-in | Supabase, EU region, Google sign-in |
| Hostnames | platform defaults; `prosit.no` subdomains deferred |

**The API ran on Fly.io until 2026-09-11**, when the trial credit ended and the
app was parked (`failed to list active VMs: trial has ended`). It moved to
Cloud Run the same day, for the permanent free allowance — 50 hours of
request-processing time a month at 1 vCPU / 2 GiB, which is roughly 9 000
calculations. Fly's realistic bill had been under a dollar a month, so the win
is the shape of the bill rather than its size: this version stays at zero with
no payment relationship to maintain. `claude/cloud-run-migration.md` has the
cost working and the cutover order.

Fly had been chosen originally because there was no existing Azure or GCP
account, so the deciding factor was time-to-running rather than tenant
alignment. That reasoning held for exactly one requirement.

`storage.py` and the deploy workflow both hold the app to **one instance**
(`--max-instances 1`), because job output lives on the instance's filesystem —
on Cloud Run, in `/tmp`, which is memory rather than disk.

The repo is public because GitHub Pages on a private repo requires GitHub Pro.
Nothing secret is in the repo: `config.js` is generated at deploy time from
repository variables, and it only ever contains the Supabase URL and the
publishable key, both of which are public by design.

## Three things that will bite again

**Paths on GitHub Pages are case-sensitive.** The repo is `Masseberegning`, so
the site is `/Masseberegning/`, and `/masseberegning/` is a 404. The API kept
working the whole time this was wrong, because `ALLOWED_ORIGINS` is
origin-only — only the invitation links broke. `FRONTEND_URL` in
`env.cloudrun.yaml` carries the capital M and a comment saying why.

**The Supabase pooler hostname contains your project's own region.** It is
`aws-N-<region>.pooler.supabase.com` and must be copy-pasted from the Supabase
dashboard, not guessed — this one is `eu-west`. Same for the project ref and
the database password. `README-DEPLOY.md` now warns about all three by name.

**rasterio's wheels are not self-contained.** They need `libexpat1` and
`libstdc++6` from the base image. Without them the container starts, fails at
`import rasterio` with `ImportError: libexpat.so.1`, and the platform answers
every request with a bodiless 503 — which the browser reports as a CORS error,
so the symptom points at the wrong thing entirely. True of Fly and of Cloud Run
alike; the lesson transferred with the app. The `Dockerfile` installs both
and then *imports the geospatial stack at build time*, so a missing system
library fails the build instead of the deployment.

## Features added after the first deployment (2026-09-10)

**An active invitation link can be fetched again.** The token used to be shown
once, at creation, and then only its hash was kept. Now the raw token is stored
alongside the hash and revealed on demand through
`GET /api/invitasjon/{id}/lenke`, which is audited. It is *not* in the
`GET /api/invitasjon` list payload — that list is loaded on every visit to the
admin page — and the atomic claim statement sets `token = null` in the same
UPDATE that spends the last use, so a used-up invitation stops being a secret
the moment it stops being useful. `test_gate.py` asserts the token is absent
from the rendered page.

The trade-off is deliberate: a recoverable link is a link that can leak from
the database. It is bounded by expiry, by `max_uses`, and by the token being
erased when spent.

**A whole domain can be invited.** Writing `@vg.no` in the invitation's "bundet
til" field creates a link anyone with a verified address at that domain can
redeem, up to `max_uses`. Stored in a separate `invite.email_domain` column,
not in `email`: a database constraint enforces that exactly one of the two is
set, and a second one enforces the domain's shape. The domain check is part of
the single atomic claim statement, so it cannot be bypassed by racing. A
single-address invitation is still capped at one use; a domain rule is exempt,
because being multi-use is the point of it.

**Saved calculations — "Mine beregninger".** Private per user. What is stored
is the *input* — polygon and parameters — plus the headline figures for the
list; not the result. Opening one re-runs it, so the numbers always reflect the
current terrain model and the overlay and downloads come back (they are job
files and expire on their own). Ownership is enforced by `user_id` being in the
`WHERE` clause of every query — no framework, one column — so each operation is
tested against another user's row, not just a missing one. Another user's row
answers 404, not 403: "forbidden" would confirm that it exists.

Two frontend details worth keeping: the polygon is stored as `[lon, lat]`,
matching what `/api/beregn` takes and *not* what Leaflet takes, and the
parameter form is read and written by a single pair of functions
(`readParams` / `applyParams`) so a field added to one and forgotten in the
other cannot make a restored calculation quietly different. Both are covered by
browser checks. Rename and delete avoid `prompt()` and `confirm()`: modal
dialogs block the page, and a two-click delete is harder to trigger by
accident.

## Deviations from the design, and why

**No foreign key to `auth.users`.** The design had
`app_user.id references auth.users(id)`. Dropped: it would require the API's
role to hold privileges in Supabase's `auth` schema, and it makes local
development and tests need a shim for a table we do not own. `app_user.id`
holds the provider's user id with no FK, and deletion ordering is the API's
job. The cost is that a deleted provider account leaves an orphan row until
`DELETE /api/brukere/{id}` is called.

**A thin Supabase auth client instead of the JS SDK.** The app vendors its
dependencies rather than using a CDN, and only four auth endpoints are needed
(`/authorize`, `/otp`, `/token`, `/logout`). `static/auth.js` calls them
directly — about 120 lines against ~50 KB of SDK, and no vendored blob to keep
updated. If more of Supabase gets used later, swap it: the rest of the app only
touches `MB.api` / `MB.url`.

**The job index was removed rather than moved.** The plan said move job output
to blob storage. What is implemented is simpler: a job's existence *is* a
directory on disk and expiry *is* its mtime, so there is no index to lose on
restart. This fixes the cold-start bug without adding a storage dependency, and
`storage.py` is the seam for blob storage when a second replica is needed.

**`LOCAL_SINGLE_USER=1` was added, which the design did not anticipate.** The
new config refuses to start without a database and an identity provider — which
would have killed the double-click `start.bat` workflow. Local mode restores it:
no database, no sign-in, every request treated as a local superadmin, and the UI
identical to before access control existed (no account chip, no saved
calculations — there is no account to own them). It is an auth bypass, so it is
fenced: the app refuses the flag on any non-loopback bind, and refuses it
alongside `DATABASE_URL` or `ALLOWED_ORIGINS`. All four guards are tested.

**`/api/revisjon` and `admin_audit.actor_email` were added.** The design had an
audit table but no way to read it. The admin page shows the last 200 events.
`actor_email` is denormalised so the log survives the actor's deletion.

## Defects the tests and the deployment found

**A malformed `X-Forwarded-For` turned into a 500 on redemption.** The header is
client-supplied and the audit column is `inet`, so junk made the INSERT fail —
on the one endpoint every new user must reach. Fixed with `db.as_inet()`, which
normalises or discards; the header is still fine as a rate-limit key.
Regression-tested with `"not-an-ip-address, ; drop table"`.

**The gate stayed painted over the app after sign-in.** `.gate`, `.account` and
`.badge` are toggled with the `hidden` attribute *and* carry classes that set
`display`, and a class selector beats the browser's built-in
`[hidden] { display: none }`. The result: an invisible full-screen overlay
swallowing every click, and a "superadmin" badge on ordinary users. Fixed by
`[hidden] { display: none !important; }` as the first rule in `auth.css`.
`test_gate.py` checks that the centre of the map is actually hittable.

**`/healthz` reported `connected: true` against a dead database.** `_open_pool`
published `_pool` before `wait()` succeeded, so the health check saw a pool
object and said yes. Two related fixes went in at the same time: the readiness
probe moved to `/readyz` with a 45-second grace period (a DB-dependent check
against a 5-second timeout fails a cold start), and `init_pool` now degrades and
retries every 20 seconds instead of raising and killing the process, so the API
comes up and answers 503 with a reason rather than not coming up at all.

**`device_commit_files` reported success while writing a stale file.** The
Dockerfile landed at 1 725 bytes instead of 3 752 and the deployment kept
failing for the old reason. Every file write to the machine is now verified
with `device_list_dir` before moving on.

Everything in this section was found by running the thing, not by reading it.
The `libexpat` failure in particular was settled by one line of `fly logs` —
which should have been asked for before any code was written.

## One piece of dead code, kept deliberately

The `count_active_superadmins` guard in `invites.py` — "this is the last active
superadmin, appoint another first" — is unreachable in practice. The actor is
always an active superadmin, so removing *someone else* can never bring the
count to zero, and the self-guard catches the only path that could. It is kept
as defence in depth for any future non-self-initiated path, and
`test_auth.py::test_one_superadmin_can_suspend_another` documents the reasoning
so nobody spends an afternoon working out why it never fires.

## Operational notes

**`prepare_threshold: None` on the connection pool.** psycopg3 promotes queries
to server-side prepared statements after a few executions. Behind Supabase's
transaction-mode pooler (port 6543, PgBouncer) a later execution can land on a
different backend session and fail with "prepared statement already exists" —
intermittently, under load, which is the worst way to find out. Disabling them
removes the whole class of failure and costs nothing: every query here is tiny,
and each request is dominated by a multi-second Kartverket fetch. The runbook
recommends the **session** pooler (IPv4, port 5432, username
`postgres.<ref>`); the direct host is IPv6-only and unreachable from Fly.

**`DEM_CACHE_MB`, previously hardcoded at 256.** A 2 GB Fly machine cannot
afford a 256 MB cache on top of a calculation's working set — a 16 Mpx DEM is
64 MB at float32 and the difference array is 128 MB at float64. On Cloud Run,
where job files are written into memory rather than onto a disk,
`env.cloudrun.yaml` sets 64 and shortens `JOB_TTL_MINUTES` to 45.

**`setup.py`.** Installs the two CI workflows into `.github/workflows/` and does
the git init/commit. The workflows are authored under `deploy/`, which is
canonical and re-synced on every run, because the remote file tools cannot
write into `.github/` — GitHub Actions files are protected. An earlier version
moved them out and deleted `deploy/`, which meant a corrected workflow could
not report itself as newer than the installed one; that is why the sync now
prints `UPDATED`.

## The move to Cloud Run (2026-09-11)

Four repo changes, and only one of them is application code.

**`db.py`: `check=ConnectionPool.check_connection, max_idle=60.0`.** This is
the one that matters. Cloud Run allocates CPU only while a request is being
served, so between requests the container is frozen: the pool's maintenance
thread does not run, while Supabase's pooler goes on closing idle connections
at the other end. Without a check on checkout, the first query after an idle
spell hands application code a dead socket — intermittently, in production, on
whichever endpoint the user happened to open first. `test_pool.py` reproduces
it with `pg_terminate_backend` and fails without the fix, which was verified by
removing the fix and watching it fail.

The tempting alternative, `--no-cpu-throttling`, switches the service to
instance-based billing where an idle instance is charged for its whole
lifetime — which is exactly the bill the move was meant to avoid.

**`Dockerfile`: `JOB_ROOT=/tmp/mb-jobs`.** Only `/tmp` is writable on Cloud
Run's first-generation execution environment, and on *both* generations every
write goes into memory and counts against the memory limit. So job files now
share the 2 GiB with the DEM cache and a calculation's working set, which is
why `DEM_CACHE_MB` dropped to 64 and `JOB_TTL_MINUTES` to 45.

**`deploy/api.yml`: build, push to Artifact Registry, `gcloud run deploy`.**
Built in Actions rather than with `--source`, because the repo is public so
Actions minutes are free and it keeps Cloud Build out of the picture. Keyless
auth via Workload Identity Federation, pinned with an `--attribute-condition`
to this one repository — without that condition the pool will mint a token for
any repository on the internet that asks.

**`env.cloudrun.yaml` replaces `fly.toml`'s `[env]`.** Committed, because
configuration that is not a credential belongs where it can be reviewed. The
JWKS URL and issuer moved out of secret storage in the process: they contain
the Supabase project ref, which is already published in `config.js` for the
browser to sign in with, so keeping them secret hid the API's configuration for
no security gain. The database URL is the only real secret and lives in Secret
Manager.

What the move does *not* change: the frontend, Pages, Supabase, every redirect
URL, `ALLOWED_ORIGINS`, `FRONTEND_URL`, and the rest of the application.

Known regression: **cold starts are worse.** Fly's proxy held the request while
a suspended machine resumed; Cloud Run starts a container from cold, and this
image imports rasterio, pyproj and shapely before uvicorn binds — 10–20 seconds
on the first request after idleness. `--min-instances 1` fixes it and costs the
whole free allowance, so it stays at 0 until someone complains.

## Still open

- **A latent 500 on re-signup.** `ensure_bootstrap_superadmin` upserts on `id`
  while `app_user.email` is unique, so a Supabase user who is deleted and signs
  in again arrives with a new `sub` and the same address, and the insert
  violates the unique constraint. Found by a test helper, documented in
  `test_calculations.py::_admin`, **not yet fixed** in production code.
- **Only Google sign-in.** Microsoft needs an Entra app registration; the email
  link needs custom SMTP first, because Supabase's built-in email service is
  capped at 2 messages per hour and is explicitly not for production.
- **Blob storage for job output**, before the machine count goes above 1.
- **Provider-side account deletion.** `DELETE /api/brukere/{id}` removes our
  record; the Supabase account survives. Deleting it needs the admin API with a
  service key, deliberately not wired into this service. For now that step is
  manual in the Supabase dashboard.
- **A privacy statement.** Storing email addresses of invited users needs one,
  plus a documented deletion route. Saved calculations add polygons — location
  data about someone's projects — which strengthens the case.
- **Rate limits are per replica** (`ratelimit.py` is in-process). Exact at one
  replica; move the counters to Postgres before scaling out.
- **No sharing of saved calculations.** Private per user by design. A shared
  or team-visible list would need a decision about who owns what.
